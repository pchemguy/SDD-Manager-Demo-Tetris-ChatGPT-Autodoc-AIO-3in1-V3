# UI, platform and release contracts

## R9 Wide and compact layout

In wide browser/desktop layout, place leaderboard, game information/controls, board, settings and controls/help from left to right. Board horizontal center stays at viewport center (within one CSS pixel rounding) for all eight combinations of auxiliary panels. Use symmetric available space around the board, not flex centering of the visible group. Game information remains immediately left of the board. Keep score, level, lines, status, in-scope preview/hold and bonus symbols legible.

At viewport widths below 1280 CSS pixels, use a compact arrangement: center the board, place essential game information above it, then optional leaderboard/settings/help sections below in that order. This responsive adaptation preserves access and board centering without tiny illegible panels. At 320 CSS pixels, no horizontal page overflow or clipped board; vertical scrolling is permitted. The board maintains 1:2 aspect ratio and uses device-pixel-aware Canvas sizing. At 1280 pixels and above, show the specified wide order. Sidebar always uses compact layout regardless of outer browser width and must resize without losing state.

Game information has individual show/hide controls for leaderboard, settings and help above its bottom gameplay row. Start/Restart occupies the left of that row; Pause/Start occupies the right. Show Start when idle and Restart afterward on the left; show Pause while running and Start otherwise on the right. Right Start resumes a paused game or starts a fresh game from idle/gameover. These are the only clickable gameplay controls; do not add movement, rotation, drop, hold or penetrator click targets. Settings form controls, file controls and visibility toggles are not gameplay-action buttons.

Save and Restore sit at the bottom of settings, with the JSON/SQLite selection accessible there. A hidden auxiliary panel and all its controls are removed from focus/accessibility navigation. Hiding settings hides its file controls. Panel toggles expose aria-expanded and retain accessible labels. Announce game status and file errors without reading every frame; do not rely on color alone for control labels/information.

Keyboard mappings: Left/Right arrows move; Down soft drops; Up or X rotates clockwise; Z rotates counterclockwise; Space hard drops; C holds; P activates penetrator; Escape toggles pause/resume for an existing game. Enter on a focused gameplay button invokes that button. After Start/Restart or resume via a button, move focus to the keyboard-focusable gameplay container so subsequent game keys work; merely focusing a settings/file control does not redirect its keys. Movement keys use immediate keydown then a 150 ms initial repeat delay and 50 ms repeat interval; soft drop repeats every 40 ms after its immediate step. Rotation, hard drop, hold, penetrator and Escape ignore repeated keydown until keyup. Clear pressed keys on focus loss/pause. Input while an input/select/button/contenteditable control has focus retains normal form/navigation behavior and does not also dispatch global gameplay. Prevent page scrolling only for handled game keys while gameplay focus is appropriate. Help lists current bindings and the active lock-policy/pause rules.

## R10 Browser and Windows shells

Browser distribution is a static build with relative, locally bundled runtime assets. Serve it over HTTP(S); file: execution is not a required target. No backend calls are needed. Test desktop Chromium and Firefox under the repository browser policy, recording actual versions, isolated binary paths and modes. Core UI/Canvas testing defaults to Chromium headless shell; full Chromium is needed only for capabilities that require it.

Windows delivery is an unsigned portable x64 ZIP. It contains the executable, Electron runtime, application assets, SQLite assets when delivered, license notices and installation instructions. Extract the archive and launch the executable; users need no Node.js or dev server. Browser delivery continues alongside it.

Electron serves only approved bundled paths from `app://tetris/` using a standard secure scheme registered before app ready and a handler on the persistent app session. Reject traversal, foreign hosts, unknown resources and external navigation/new windows. Resolve workers and WebAssembly through the same packaged origin, with an explicit CSP allowing the bundled SQLite runtime. Keep nodeIntegration disabled, contextIsolation enabled and renderer sandbox enabled. No preload bridge is required for ordinary game/file functionality. Window blur pauses; close ends that desktop session. Packaged asset and cookie/query behavior are verified through the shared runtime and shell checks available on the execution host; native Windows launch is separately reported if unavailable.

## R11 Sidebar delivery and lifecycle

Chromium uses a Manifest V3 `side_panel` entry and `sidePanel` API; Firefox uses `sidebar_action` and a supported background script. Both load a packaged shared app page and bundle JS, CSS, icons, schemas/validators and WebAssembly. Use minimum versions supporting the selected APIs: Chromium 116 and Firefox 115; implementation confirms manifest/tool compatibility before packaging. No remote scripts, eval-generated validators, host-page content script, backend or server is needed. Request only storage plus the platform sidebar permission where applicable. Open the sidebar from its extension action using a user gesture.

The board, essential info, two gameplay buttons and auxiliary toggles stay accessible in a 320–600 CSS pixel sidebar; at smaller supported widths scale the board to available space. Auxiliary panels become collapsible vertical sections. Preserve every in-scope setting, leaderboard entry and file action. Hiding settings hides Save/Restore here too.

Persistent settings use storage.local; ephemeral game/results use storage.session under a browser-window key, as defined by API-DESIGN. On initial opening without a checkpoint, show idle. Acquire writer generation, validate any checkpoint and restore a running/paused game as paused. Do not apply closed wall time. Persist a coherent checkpoint after commands and at most every 100 ms of active timer advancement; acknowledgements define the durable state. If storage fails, pause and show an error; do not claim the last unacknowledged transition is recoverable. The background context handles message ordering and window cleanup only. No interval/game engine runs there.

Closing/reopening preserves the last acknowledged session data in the same browser window. A browser restart or window close ends it. A malformed internal checkpoint is discarded with a clear warning and a fresh idle state; valid persistent settings remain available. Stale generations/revisions are rejected without overwriting the current session. Extension settings changes in one window are read by another on its next opening; this does not synchronize their active games.

Save uses a Blob download and Restore a file picker with identical portable content. Extension-local settings replace cookie/query side effects; host page URLs and cookies remain unchanged. Browser download permission is added only if the selected implementation actually needs an extension downloads API; a normal DOM download is preferred.

Chromium's development ZIP is extracted and loaded unpacked. Firefox's unsigned development ZIP is installed temporarily through about:debugging and is not represented as a permanently installable signed add-on. Browser and Windows packages remain included in the same release. Full-browser native sidebar open/close evidence is distinct from adapter-model and shared-page tests; unavailable facilities are explicitly excluded and unverified, not silently counted as passed.

## R12 Versioned releases and package verification

Choose v0.1.0 for the classic browser baseline, increment minor versions for bounded capability phases, and use v1.0.0 when the complete requested scope and all platforms have their applicable verification. Patch versions cover corrective releases without broadening scope. PLAN assigns the exact phase/version map.

Every completed implementation phase is verified and explicitly integrated into main before its release commit/tag. Publish a GitHub release containing release notes, installation instructions, checksums and all applicable deployable/installable artifacts built for its exact source. Stable names are `tetris-browser.zip`, `tetris-windows-x64.zip`, `tetris-chromium.zip`, `tetris-firefox.zip`, plus `INSTALL.md` and `SHA256SUMS.txt`. Do not embed versions or opaque build hashes in release-asset basenames; internal bundled chunk names may be content-addressed.

For every asset, verify archive readability, expected root/manifest/entry, version agreement, required local assets, absence of development secrets/dependencies and runtime source identity. Re-download hosted assets and compare bytes/checksums to the verified local artifacts. Browser packages must run from extracted content in the supported runner. Electron packages additionally require runtime/executable metadata and asset-origin checks; native launch limits remain disclosed. Extensions additionally require platform manifest/CSP validation, sidebar entry resolution and shared-page/adapter behavior, plus native integration where available. Packaging success alone does not satisfy these checks.

Release notes identify delivered capabilities, artifact installation, unsigned/temporary development limits, actual checks and excluded native/full-browser evidence. No package or platform is called delivered before its feasible required checks pass. Do not substitute a source archive for the requested runtime packages.
